# Performance waste audit for v0.2.10

Date 2026-10-11. Repository main after the v0.2.9 tag (code read at `ad6d02a`, the PR #50 merge; Max's PC measured at the tag `079f6ebe`, which differs only by test-wait changes), read-only: no code was changed for this report. Thread "Performance waste audit (Fable)".

## What this audit is

Max's bar: find the glaring mistakes of the Ambient Occlusion kind (the AO kernel ran four times per pixel under MSAA 4 and its exclusion mask redrew every scene as a whole extra pass), not micro-optimisations. Every hot path was judged by three checks, and each finding below names the one it fails:

- **Rate**: it runs per X, but its result only changes per Y (per sample vs per pixel, per tick vs per world change, per frame vs per network update).
- **Scope**: it touches everything when only a subset matters (all bricks for one changed brick, all avatars for the ones in view, all particles for the ones that can be seen).
- **Trigger**: it runs because time passed, not because anything relevant changed (rebuilds, physics steps, GPU redraws of static content).

A finding is in the ranked list only if it fails a check by about 4x or more, is on a path a player hits, and can be measured on Max's PC with existing tooling. Smaller things, and things that would need a rewrite to prove, are in the appendix so nobody re-audits them.

Confidence labels: `confirmed inefficiency` (call chain traced in the code, the repeated work is real and on a hot path), `plausible hotspot` (suspicious, needs the named measurement), `already optimized` (checked, the code avoids it).

## How it was done

1. Seven read-only code audits in parallel (world rendering and shadows; particles, lights and weather; physics; bots; brick edits and world updates; events, Add-Ons and networking; the client frame loop, avatars, items and UI), each counting how often every hot loop runs per frame, tick, brick, light or bot before estimating cost, with every line number verified by reading. Their raw notes (2,000 lines) are summarised here; the counts in this report are from the code, the costs from the measurements below.
2. Measurements already on file: the Bedroom benchmark runs D and E of 2026-10-11 (RTX 4070 SUPER, 200,187 bricks, 151 light bricks, 488 emitter bricks, 3440x1440, Max's settings; `bedroom-perf-run-D.txt` and `-E.txt` in the project files), the shadow and shading runs in `docs/progress/2026-10-11-shadows-shading-performance.md`, the frame-spike evidence in `docs/progress/2026-10-11-frame-instrumentation.md`, and the 32-bot server profile in `bots/bot-performance-2026-10-11.md`.
3. New measurements for this audit: Max's v0.2.9 session logs and a fresh `large_build_perf` run with the CPU sample profile on his PC (section "Measurements"), and a server-side sample profile of the content-free bot benchmark in the cloud container.

One correction to the earlier profile reading: the 32% of samples in `Device::poll(Wait)` in run D is the benchmark's own per-frame wait for the GPU (`crates/client/tests/large_build_perf.rs:437`), not the game's. The player frame path has no blocking GPU wait or readback (checked: every `PollType::Wait` in the client is a one-off at startup, the once-per-adapter Add-On calibration, or an offscreen probe). In real play the main thread's wait is the swapchain acquire at the 165 Hz vsync. So the real CPU work in run D is the other 68% of samples, and the shares below are quoted against that.

## Ranked findings

Ranked by estimated impact on what a player feels (frame time on a big build with bots first, then server tick with bots, then hitches, then networking). Costs marked "measured" come from the runs in "Measurements"; "estimated" is arithmetic from the counts and needs the named benchmark before a fix PR is cut.

### 1. Every emitter brick on the map is simulated every frame, seen or not

- **Check failed**: Scope (all 488 emitters and all live particles, for the few whose cloud can reach the view), and Rate (particles integrated per render frame, 144-165 Hz, for a cosmetic that v20 stepped at 32 ms).
- **Where**: `crates/client/src/effects.rs:186-190` selects every attachment under the 4096-source limit; `crates/fx-runtime/src/world.rs:652-695` steps and emits for each; `world.rs:643-647` integrates and compacts every live particle; the only frustum test is on finished particles inside `snapshot_culled` (`world.rs:839`, `880`).
- **Count**: per frame, 488 emitters stepped and ~44,000-65,536 particles integrated, then every in-view particle is sampled, sorted and copied four times on the way to the GPU (`snapshot_in_view` samples colour twice per particle, `world.rs:844-849`; copies at `world.rs:1011`, `app/mod.rs:1451-1467`, `fx-runtime/src/gpu.rs:358-387`). Necessary: the emitters whose reach overlaps the view or a flare distance of the eye, a small fraction of 488 in a many-room build, and one copy.
- **Cost**: measured. Run D profile (Bedroom, 200k bricks, 488 emitters, 44k particles drawn): `snapshot_in_view` 19.7% + `WorldEffects::advance` 7.7% + `combine_effect_frames` 4.4% + `EffectsRenderer::write` 3.8% + most of `Vec::from_iter` 3.9% of samples, which is about 40% of the frame's real CPU work (the rest of the samples are the benchmark's GPU wait), roughly 3 ms of a 8.5 ms frame, every frame, camera still. Upload is 64 B x sprites + 128 B per view = 2.8 MB per frame at 44k sprites (`particle_upload_bytes` in `probes.rs:298`).
- **Fix**: in `WorldEffects::advance`, pass `emitting = false` for a source farther than a cosmetic radius from every eye or outside the frustum expanded by its authored reach (max speed x lifetime + extents); `SourceOptions::emitting` already drains such a source correctly (`world.rs:662-692`). Then skip integration for particles of paused sources outside the expanded frustum. Separately, in `snapshot_in_view` sample once per particle, keep the scratch Vecs on `EffectsWorld`, and let `combine_effect_frames` move the one non-empty list through instead of merging three.
- **Correctness**: pixel-identical for anything inside the view (the margin must cover travel); paused sources keep their emission clock (`source.next = end + period`) so re-entering a room does not burst; emitter RNG sequences change only for paused sources (cosmetic, no replay or protocol impact); sprite order stays stable far-first.

### 15. Every brick candidate on every bot ray resolves its definition by string, twice

- **Benchmark**: `bot_deathmatch_stress` with a counter of `Definitions::get` calls per tick.
- **Confidence**: confirmed inefficiency.

### 17. The item world and the Add-On script view are rebuilt every frame or tick whether or not anything changed

- **Check failed**: Trigger and Rate.
- **Where**: client: `crates/client/src/world_items.rs:391-777` (`sync`: `view.validate` walks every static item, projectile and drop every frame, `:405-406`; a `Candidate` with String clones per static item per frame; a distance sort with the distance computed inside the comparator, `:728-745`), `:1403-1416` (`PoseKey` keyed on the raw f32 time, so every in-flight projectile of an animated model gets its own geometry slot, CPU re-pose and vertex upload every frame), `items.rs:1278-1311` (`moved_mount_transform` re-samples the held image's bind pose per image per frame to recover a per-model constant).
