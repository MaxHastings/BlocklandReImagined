# Locomotion lane: design note for the next three items

Written 2026-10-07 by the locomotion thread; updated after review
(independent design review, 2026-10-07): throttle 0.8, handling kept per
definition instead of a serialized key, a hard limit before any warm-up,
warm-up only at a bot's join, shove limits written down.

First written after measured moves (jump,
jets, jump-and-crouch into openings) went up at 2515cce. Nothing below is
built. Each item reuses the seam that is already on the branch:
`crate::reach` runs the real code once per mechanical configuration on a
bare floor, deterministically, and shares the result. Order: vehicles, then
warm-up at load, then shove landing.

## 1. Vehicles: measured stopping and turning

**Today** (`session/bots/interactions.rs`, the driver; `route.rs`):
- stopping distance = `speed * 0.3 + speed² / (2 * brake_force / mass) + 1`
  (guessed reaction time, idealised braking, a guessed margin);
- arrival speed = `sqrt(2 * brake_force / mass * distance)`;
- turn speed = `sqrt(CORNERING * radius)` with `CORNERING = 10` for every
  chassis; tightest radius from wheelbase and lock geometry, with a
  `0.6 * length` fallback;
- the hazard check (ally on foot, hull sweep) runs straight ahead along
  the nose, even mid-turn.

**Proposal:** `reach::Handling::of(definition, scale)`.
- Runs the real `bri_vehicles::VehiclesWorld` on a flat test floor with
  the bot's own steering prefs (mouse steering, lock holds), so it uses
  the same code as driving a vehicle.
  - one straight run: full throttle to top speed, then brake to a stop,
    which gives stopping distance from every speed it passed through;
  - three turning runs from rest at full, half and quarter lock, speeding
    up, which give the path curvature at each speed and so "the fastest
    it holds a turn this tight".
- It replaces all four numbers above (the two formulas, `CORNERING`, and
  `route::Chassis` with its fallback), and they are deleted.
- The hazard check sweeps the arc the chassis is actually on (yaw rate /
  speed, never tighter than its measured tightest turn). It sweeps in
  short chords out to the measured stopping distance: the hull cast and
  the ally check run on each chord. The actual-hull checks stay
  authoritative; only their path changes.
- A wheeled vehicle that will not drive on the test floor is treated as a
  lost affordance (the bot gets out), like a wreck is today.

**After review:** measured at the throttle the driver uses (0.8), not
1.0. The handling is measured once per definition and scale, when a bot
first looks at that definition, and kept with the loaded pack (an
`Arc<Handling>` per definition and scale); a pack reload drops them. No
serializing on lookup.

**Known limits, said plainly:**
- reverse stopping reuses the forward table;
- it does not cover slopes or surface friction (the hull checks and the
  existing no-headway give-up still catch those);

**Cost (measured):** the test car takes 6,978 vehicle physics ticks
(58 s simulated, a few hundredths of a second of real time), once per
definition and scale of a loaded pack. One measurement is capped at
`BUDGET_SECONDS` (120 s simulated) across all its runs; past it, it keeps
the turns it read. The key is the pack's fingerprint, the definition id
and the scale, so nothing is serialized on lookup and a reloaded pack is
measured again.

**Tests (sanity only):**
- three times the brakes stop shorter;
- half the lock turns wider;
- one measurement shared, and an edited definition measured again;
- the route gear and pace tests rewritten on a measured car;
- every existing vehicle bot test passes unchanged;
- one new chaos test: a driver mid-turn brakes for an ally standing on its
  arc, not on its nose line. **Not done:** it needs a controlled turn, not a
  pursuit (two tries either passed with the arc sweep off or put the ally
  beside the target); it goes with the warm-up item.

## 2. Warm measurements when tunings load

**Today:** the first bot that plans with a new tuning pays the measurement
inside a tick (~90 ms for a body; vehicles will add their own).

**Proposal:**
- Call `Reach::of` for every tuning the session can spawn, at the point it
  learns them: the default tuning, each archetype's tuning when the
  archetype catalog loads (`self.archetypes.tuning(..)`, used at
  `session/packages.rs:2119`), and a scaled tuning the moment a player is
  scaled.
- Call `Handling::of` for each wheeled definition when the vehicle pack
  loads (`session/vehicles.rs:391`).

Replay is unaffected: a measurement is a pure function of its key, so
warming changes only when it runs, never what a bot plans. It stays
on-thread (no background thread), so a load takes the measuring time once,
up front.

**Touches:** two or three one-line calls in session load code. Those are
shared files, so I'll tell the coordinator before the change.

**Test:** after load, planning with every archetype finds the measurement
already there (the shared `Arc` is the same one).

**After review, this replaces the proposal above:**
1. First a hard limit on one measurement, a named number of simulated
   ticks shared by its runs. Past it, the measurement keeps what it has:
   the jet grid stops growing (legs past it take the last measured rate,
   as beyond the grid today), and the ledge bisection stops narrowing and
   keeps its last height known to land. It stays deterministic, because the
   limit counts ticks, not time.
2. Warm-up only for what a bot will use: its own tuning, when the bot
   joins. Not every archetype at map load, and not a player's scale
   change. Vehicles: when a bot first looks at a definition.
3. The join call goes in shared session code; I'll tell the coordinator
   before the change.

## 3. Shove landing (half of plan item 7)

**Proposal:** `reach::landing(tuning, push, from) -> Landing`.
- Runs the real player motor in the air from a standing body given the
  shove's impulse (the capability's `push` velocity), with no input and no
  map, and returns the flight: the horizontal reach it lands at for each
  drop height below the start (a short table), and the speed it lands at.
- The fighting lane puts that flight onto the map (the first floor under
  its arc) and asks the harm reader what a fall of that speed does there.

So this lane gives "where a body flies", the capabilities lane gives "what
landing there costs", and the fighting lane joins them. Nothing reads a
map or a brick name.

- **Cached** per (tuning, push), with the push rounded to its declared
  value (pushes are item data, a handful per session).
- **Not covered:** air control (the target can steer while flying; we
  predict no input, like `route::landing` already does for a bot's own
  hops).
- **After review:** the doc comment states both limits: it predicts a
  standing target (a running target's own speed is not counted), and it
  assumes no air control. The push outcome judge (plan item 7) corrects
  both. The cache key is the tuning plus the push's full vector,
  vertical part included. Follow-up, recorded in the plan once the harm
  reader exists: `nav::Body.drop` (a flat 4.0 today) reads the same fall
  rule, so "a drop it walks off" and "a drop that hurts" agree.
- **Test:** a stronger push flies farther; lower gravity flies farther;
  a push straight up lands where it started.

## Not proposing

- **Horses** (stretch). A horse is a player-type mount with its own
  `PlayerTuning` (`bri_vehicles::actor_tuning`), so `Reach::of` already
  measures its jump. Whether the walk grid can plan for a mounted body is
  a separate question; I'll look only if the three items above land clean.
