## 1. Loop 3: stock behaviour as data

**Today.** `weapons/src/runtime/stock.rs` turns an image's datablock name into
a `Stock` record of 13 fields, and a projectile's name into `StockProjectile`.
The runtime reads that record in 17 places. These are the groups:

| Group | Fields | Vanilla Add-On |
|---|---|---|
| Arm moves | `charge_arm`, `prefire_arm`, `throw_arm`, `recoil_arm` | Spear, Sword, Gun, Horse Ray, Push Broom, Key, the building tools |
| What `onFire` does instead of launching | `fire` (HostTool, Skis, Key, ShootBasketball), `host_tool` | the building tools, Item_Skis, Item_Key, Item_Sports |
| Second hand | `left_image` | Weapon_Guns_Akimbo |
| Sports | `throw`, `aimed_throw`, `spawn_grace_ticks`, `thrown`, `sport_keys`, `ball`, plus `StockProjectile::{Dodgeball, Football}` | Item_Sports |
| Hit effect | `StockProjectile::HorseRay` | Weapon_Horse_Ray |

Every one of these Add-Ons is vanilla (`addon-import/src/reference.rs`,
`VANILLA`). Vanilla weapons go through `weapons-import`. That importer reads
datablocks but not script bodies, which is why the table exists.

**Design.** The importer fills fields and the runtime reads only fields. There
are three kinds of move:

1. **Read from the script body where the script says it.** `addon-import`
   already reads `playThread(2, X)` in Add-On state scripts and sets the
   state's `arm` (`ports/shots.rs:432`, `scripted`). Make that reader one
   function that both importers call. The vanilla images then get their arm
   moves the same way an Add-On's do, with no names involved. The akimbo's
   left hand comes from the same kind of read: `mountImage(X, 1)` in `onMount`
   fills the existing `Image::left_image`. Any Add-On akimbo gets it free.
2. **Declared in data, with a table in the importer where no generic read
   exists.** `hammerImage::onFire` and the other tool scripts call engine
   functions that no reader can turn into "break bricks". These get a new
   image field, `on_fire: Option<OnFire>`, where
   `enum OnFire { Tool(HostTool), Skis, Key }` (marked not stable). The vanilla
   importer sets it from a small table keyed by datablock name. That table is
   the only name list left after this, and it lives in the importer, outside
   the runtime dependency graph, as `AGENTS.md` asks. An Add-On can write
   `on_fire` itself. `bri_weapons::host_tool` keeps its signature and reads
   the field, so `session/tools.rs` does not change.
3. **Item_Sports and Horse Ray.** My earlier plan (§9) kept Item_Sports as a
   documented port. The new contract says every content-name read goes, so
   this proposes moving it too:
   - `Image::sport: Option<Sport>`, where `Sport` holds the throw speeds,
     aimed throw, spawn grace, thrown and keys;
   - `ProjectileDef::sport: Option<SportHit>`, where `SportHit` is knockout
     before bounce or catch-and-score;
   - `ProjectileDef::turns_into: Option<String>`, a player type id, for Horse
     Ray.

   The importer sets these by datablock name, like `on_fire`.

   The cost is that schema fields only vanilla uses today get marked not
   stable. The gain is that `stock.rs` is deleted and the runtime's name ban
   (`the_runtime_never_matches_datablock_names`) becomes total. **The reviewer
   should decide whether this is worth its fields.** If not, Item_Sports stays
   the one documented port.

**Client.** `client/src/building.rs:82` has `Equipment::{Hammer, Wrench,
Printer, Wand}`, which are picked by item. These become one
`Equipment::Tool(HostTool)` read from the held image's `on_fire`. Nobody owns
that file, so I'll tell the coordinator before editing it.

**Also found.** The hammer's bot capability (`bots/combat.rs:170-181`) has
bare `5.0` reach and `10.0` damage. Loop 3 replaces them with the numbers from
the hammer's data, or with constants that name their v20 source if the data
does not carry them.

**Proof.**
- Replay: the PC thread records a match with stock weapons on main and plays
  it back on the branch with identical checksums. This needs the regenerated
  packs, so it runs on the PC.
- Importer test: replay digests may not cover arm animations, so this test
  compares every vanilla image's arms, `on_fire`, left hand and sports values
  against what the old table gave.
- Content: content regenerates on the PC. The PC thread then takes the three
  `blockhead_bot` known failures off the list (contract §9).

**Deletes:** `stock.rs` (or everything but Item_Sports, per the decision
above), `StockFire`, four `Equipment` variants, and the hammer's bare numbers.

## 2. Timed throws (grenades)

**Today.** The bot's native reader refuses an image with `cook`
(`tactics.rs:400`). It also refuses any projectile with `children`
(`tactics.rs:431`), and Add-On grenades usually have children for shrapnel and
smoke. So bots never use grenades.

**The data already says everything.**
- When a projectile goes off in the runtime (`runtime.rs:3634-3644, 3790-3830`):
  - a cooked shot's remaining fuse runs out (`fuses`);
  - it reaches `lifetime_ticks` with `explode_death`;
  - it hits something at or after `arm_ticks`;
  - it hits a player with `explode_player`;
  - it is not `ballistic`;
  - it reaches `max_bounces`.
- How it bounces: `elasticity`, `friction`, and sticking by `min_stick_speed`
  and `bounce_angle`.
- How long the fuse burns: `Cook::fuse_ticks`, minus the ticks from the
  pin-drop state to the fire state. That walk over the states is the same one
  `cadence()` already does.

**Design.**
- **One more delivery kind:** `Delivery::Timed { flight, fuse_ticks }`. It is
  chosen when the image has `cook`, or when the projectile is ballistic and
  would bounce rather than burst on its first hit (`arm_ticks > 0` and not
  `explode_player`).
- **No second physics model.**
  - I take the bounce from `runtime.rs:3817` and the burst conditions above,
    and turn them into two public functions in `bri_weapons::runtime`:
    `bounce(def, velocity, normal)` and `bursts(def, age, bounces, hit, fuse)`.
    The runtime and the bot predictor both call them.
  - The predictor then runs the existing per-tick flight
    (`tactics::flight_position`). At each world hit it applies `bounce` and
    asks `bursts`.
- **Aims.**
  - Candidates are the aims the splash chooser already makes (body, feet, a
    surface beside the target), each on the low and the high arc. No new
    aim-search loop.
  - For each candidate, the predictor follows the throw to where it goes off.
    The candidate counts when that point is within the splash radius of where
    the target will be at that moment.
  - The splash scorer and `safe_blast` then use that point and time as the
    impact. `safe_blast` already catches a throw that bounces back at the bot
    or an ally.
- **Budget.** A fuse can be longer than `PATH_TICKS` (256). Rays are cast
  over chords several ticks long. The chord length comes from the
  projectile's own fall: the largest number of ticks whose arc bulges less
  than the projectile's radius. A long fuse therefore costs fewer rays, and
  no new constant is needed. Positions stay exact per tick. Rays come from the
  shared budget and a candidate can finish over several ticks, as curved
  shots already do. `bot_think_time_16` gates it.
- **Children** (decision for review). The native reader stops refusing
  projectiles with children and counts the children's damage as zero, an
  honest underestimate. Without this almost no Add-On grenade qualifies. The
  side effect is that some other Add-On weapons with children, such as flak
  or cluster launchers, also become usable by bots, valued by their main
  burst only. Auras (fire, gas) stay refused.
- **Not in this version:** cooking (holding the pin so it goes off in the
  air), which is a second trigger style. A bot throws as soon as the states
  allow.

**Vanilla check before merging.** I'll list every vanilla projectile that the
Timed rule picks up. If one changes how bots use a stock weapon, I'll say so
in the PR, because "nothing changes for vanilla" is not assumed.

**Waits for:** fighting's origin parameter on the candidate chooser (row 3),
and loop 3 (row 4). I'll merge main in before touching the candidate loop.

## 3. The harm reader (for row 7)

**What it answers.** If this body lands here, moving this fast, how much
health does it lose?

```rust
/// Not stable until the modding API freeze.
pub(crate) fn landing_harm(session: &Session, target: OwnerId, landing: &Landing) -> f32
```

`Landing` is the locomotion lane's shove prediction from `reach.rs`: the
touchdown point, the impact velocity, or "falls out of the world". I take that
type as they define it. The harm is the sum of three parts, capped at the
target's health:

1. **The fall rule.** This is the same code that hurts players today
   (`session/combat.rs:2440-2489`):
   - the minimum impact speed scaled by height;
   - the falling-damage permission from the minigame or server;
   - the admin-wand exemption;
   - `SPEED_DAMAGE_SCALE`;
   - guards.

   I'll pull that body out into one `fall_damage(owner, impact)` function that
   both the real impact handler and the reader call, with no behaviour change.
   `session/combat.rs` is a shared file, so I'll **ask the coordinator first.**
2. **Kill bricks.** These are bricks at the touchdown point whose events say
   that touching them kills or hurts the toucher. Only unconditional outputs
   count. Anything behind a condition counts zero, an underestimate that will
   be stated in the code. This reads the events runtime and never a brick's
   name.
3. **Out of the world.** A landing that never lands, or that ends below the
   world's lower bound, is worth the target's whole health. I'll confirm where
   players' lower bound lives before building. `packages.rs:61` `KILL_Y` is
   for package entities, so it may not be the right one.

**The swap.** Pushes currently score `PUSH_WORTH` (`tactics.rs:11, 605`).
`tactics::Context` gains `push_worth: f32`, supplied by the fighting lane's
consequence worth. That consequence worth is the harm from this reader plus
whatever it adds for objectives. Then `PUSH_WORTH` is deleted, in the same PR
that wires the consequence worth, so the flat number never sits next to its
replacement. I write the tactics side; fighting writes the adapter.

**Not mine:** "a push toward your own goal is worth less than nothing". That
is consequence worth in the fighting lane, using the same landing.
