# v0.2.1 performance investigation

Scope: the reported 6-versus-6 / 16-bot battles in Bedroom with AMC City or
Beta City 16, using Gun, Rocket Launcher, Gravity Gun and Spear. No interactive
playtest or visible client was launched. Measurements below are headless macOS
Apple M1 Pro (10 cores, 16 GB); Windows frame-rate behavior remains unmeasured.

## Correctness and measurement boundary

The first change in `Simulation::walk_bricks` replaces its per-ray duplicate membership guard
from `std::collections::HashSet` to `rustc_hash::FxHashSet`. The guard is never
iterated; ordered spatial buckets continue to determine candidate traversal,
ties, nearest-hit updates, early exits and calls to the supplied acceptance
predicate. Collision, perception range, tick scheduling and gameplay budgets
are unchanged. A second measured change passes the already fetched `&Brick`
from the acceptance check into private `ray_brick`, removing an identical
lookup in the persistent world map. The ray still gets the same brick, bounds,
definition, collision shape and transform. Keys are numeric authoritative brick IDs, not client-supplied
strings; planting allocates IDs on the host. Fx hashing is noncryptographic,
so it does not add hash-flood resistance for deliberately chosen imported IDs.
The spatial index already uses Fx hashing. No broader replacement of untrusted
string maps is intended.

The existing harness's `shots` field summed live projectiles on every tick. It
is now labeled `active_projectile_samples`; `observed_projectiles` counts unique
projectile IDs seen after steps, a lower bound on spawned projectiles because
a projectile may spawn and disappear within one step. Neither is an accuracy
metric. Sampled snapshot bytes and brain state produce a deterministic evidence
digest for paired runs of the same executable/toolchain/input. This is a
regression comparison, not a portable persistent identity.

Snapshot construction and MessagePack encoding diagnostics run once per 120
ticks outside the step-time window. The host does **not** send this full-world
snapshot per step. Phase labels, exact world selection, adjustable weapon-phase
length and a stop-after phase make bounded sampling reproducible. No hard wall
clock acceptance threshold was added.

## Existing evidence

The earlier debug capture identified `bot_sight -> Simulation::sight ->
target_filtered -> walk_bricks`, including standard HashSet insertion/growth,
as a major stack branch. The 960-tick pre-change debug Beta City 16 medians were
7.514 / 4.632 / 5.015 / 3.911 ms for Gun / Rocket / Gravity Gun / Spear. Two
FxHashSet runs gave 6.779 / 3.834 / 4.538 / 3.779 and
6.748 / 3.762 / 4.442 / 3.777 ms. That suggests useful query savings but is
not an optimized build or shipped Windows FPS result.

A previous debug run had a 132 ms Spear outlier (and an earlier run a 141 ms
outlier). Later repeat runs did not explain these. Average query improvement
must not be presented as a demonstrated fix for intermittent hangs.

## Repeated optimized stack capture and long run

A 5-second, 1 ms macOS `sample` capture was repeated on 20,000-tick Gun
runs using the original HashSet baseline and the final Fx/reference variant.
The top-of-stack summary gives ordered-map lookup samples of 587 / 2,423

Navigation's `Nav::floor` has 33 self samples in each capture. The next

## Host and client stall boundary (read-only source audit)

- `crates/net/src/server.rs` measures `session.step()` in `PerfWindow`, then
  constructs pose/20 Hz replication updates and performs broadcast encoding
  outside that timer. The displayed host step time cannot rule out replication
  or serialization stalls. World-transfer encoding for joins runs off-loop.
- `Session::snapshot()` clones an `imbl::OrdMap` world, then derives weapon,
  inventory and player state. The world clone shares persistent storage;
  encoding a full snapshot still scales with brick count.
- `WorldEffects::sync` returns immediately when the incoming `Arc<PublicWorld>`
  identity is unchanged. It scans all effect attachments when world identity
  changes, including rocket brick edits. This can create update-dependent
  client cost, but no measured stall is attributed to it yet. The network
  worker replaces this Arc only on `world_changed` or map change; ordinary
  player/projectile pose updates preserve it.
- Weapon effect reconciliation builds per-frame sets/maps for projectiles.
  Actor and world effect advancement include CPU occlusion/collision callbacks.
  Effect snapshots allocate particle/light arrays. Particle snapshot sampling
  switches to Rayon above 4,096 particles per partition, so pool scheduling is
  another workload-dependent boundary to measure. Particle depth ordering uses
  radix sorting; combining three effect frames uses a linear merge.
- GPU effect preparation, terrain updates, scene changes, lighting and portal
  views happen outside `Session::step`. The supplied Windows FPS log's
  alternating 6.1/50.2 ms values identify frame symptoms only. A render-thread
  stack plus host timing and effect/brick counts is needed to localize them.

## Integrated objective/combat measurement, 2026-10-03

After central integration and final correctness/clippy checks, the current
optimized engine was measured sequentially without profiling or another Cargo
build started by this lane. Each distribution below is run 1 / run 2 in ms,
with 2,400 ordinary 120 Hz steps per phase. The synthetic scene has 16 actual
objective-enabled NPCs, authored spawners, ordinary mini-game inventory and
creator event rows. Each mixed phase starts a fresh ordinary session so an
earlier objective victory cannot turn it into a benchmark of a finished round.
Timing assertions are absent; assertions require real control/progress evidence.

|---|---|---|---|---|
| Four independent latches | 0.092 / 0.092 | 0.205 / 0.195 | 0.333 / 0.262 | 0.649 / 0.453 |
| Mixed combat + four latches | 0.107 / 0.105 | 0.241 / 0.239 | 0.361 / 0.355 | 0.611 / 0.606 |
| Eight independent latches | 0.087 / 0.084 | 2.593 / 2.575 | 2.659 / 2.640 | 2.856 / 2.874 |
| Mixed combat + eight latches | 0.111 / 0.109 | 2.636 / 2.612 | 2.720 / 2.735 | 2.923 / 2.925 |

**Four independent latches compose and win; eight unordered independent latches
currently exceed the admitted search model.** This is a practical expressive
ceiling for creator rules, not a successful eight-latch plan. Eight-latch phases
reported `objective planning budget/model limit` in 36,488 controller samples
per phase, zero objective-control samples and zero objective scores. The model
retains its declared 256-node/4,096-candidate bound; no budget was enlarged to
force success. Combat remained active and dealt real damage in that scene.
Future goal-directed search is a measured next question.

Four-latch quiet control produced 19,277 objective controller-ticks and one
authored score of 17. Four-latch mixed control produced 19,417 objective
controller-ticks, score 17, 761 fight controller-ticks and actual damage.
Both mixed phases observed 41 distinct live projectile IDs and 761 fight
controller-ticks. These counters and diagnostics matched across repetitions.
Projectiles that spawn/hit/expire within one step can be absent from this count;
canonical damage supplies independent evidence of combat delivery.

Active fight/objective steps are reported separately: four-latch quiet has
1,214 active steps with p50/p95/p99/max 0.095/0.204/0.270/0.419 and

this scene; this is an inference from phase composition and diagnostics,
